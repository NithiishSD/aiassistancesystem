# Fix retrieval first, then spend quota wisely

Zedek's biggest quality losses come from its retrieval layer, not from its choice of framework. The best-known open-source assistants (Open WebUI, OpenHands, Letta, Goose, Home Assistant Assist, OpenClaw) all ship features Zedek does not have, and the ones most worth copying are small. The first is a cross-encoder reranker over a wider candidate pool, replacing the hand-tuned L2 cutoff of 1.0. The second is BM25 hybrid search for exact tokens such as course codes and roll numbers. The third is schema-constrained JSON on every provider in the chain. Together these are about three days of work for a solo student, and none needs a GPU. The second priority is efficiency under free-tier quotas: move scarce providers down the chain, track quota before sending requests, order prompts so provider caches can hit, and stream replies into TTS. Home Assistant measured that last change cutting time-to-speech from 5–6 s to about 0.5 s. The third tier comes from the agent projects: one-folder capability manifests (these fix the "edit 4 files" problem), always-in-prompt core memory blocks, a context condenser, and stuck detection in the watchdog. Most of the published gain figures come from large corpora or from vendors, and none were measured on a few hundred personal facts. The first job is therefore a 30–50-query retrieval eval set, which extends the routing eval harness that is already planned, so each change is measured on Zedek itself.

## Eight projects, one convergent design

The open-source assistant field has settled on a common shape, and it is close to what Zedek already has. Each system runs a simple LLM⇄tool loop, extends through MCP, and wraps capabilities in self-describing units. **Open WebUI is the adoption leader at about 153.5k GitHub stars**. It is followed by Home Assistant core (91k), OpenHands (about 89.5k), AnythingLLM (66.6k), Open Interpreter (68.5k), Goose (54.8k), LibreChat (45k), Jan (44.7k), Khoj (37.5k), Letta (about 25k) and Leon (17.6k) ([GitHub API](https://api.github.com/repos/open-webui/open-webui); [OpenHands](https://github.com/OpenHands/OpenHands); [Goose](https://github.com/block/goose); [Letta](https://github.com/letta-ai/letta)). OpenClaw reached **247,000 stars by March 2026** ([Wikipedia](https://en.wikipedia.org/wiki/OpenClaw)). It also shows that popularity and suitability are different things, as the list at the end explains.

None of these projects should replace Zedek, and each one is best at a different thing that Zedek can copy.

| Project | What it does best | The idea to take for Zedek |
|---|---|---|
| Open WebUI | Most complete documented RAG stack: BM25 plus a cross-encoder reranker, a relevance threshold, citations and a full-document mode ([docs](https://docs.openwebui.com/features/chat-conversations/rag/)) | Hybrid search plus a reranker plus a threshold |
| Home Assistant Assist | Local-first voice. The local intent engine runs first and "only questions or commands it can't understand" go to the LLM ([HA blog](https://www.home-assistant.io/blog/2025/09/11/ai-in-home-assistant/)) | Streaming TTS, a grammar-limited STT, and passing context on to the LLM |
| OpenHands SDK | Reliability: a condenser, stuck detection, and risk labels on actions ([arXiv 2511.03690](https://arxiv.org/abs/2511.03690)) | Condenser and stuck detection inside `watchdog.py` |
| Letta | Memory: labelled, size-limited "core" blocks plus background "sleep-time" consolidation ([Letta](https://www.letta.com/blog/memory-blocks/)) | 2–3 always-in-prompt core blocks |
| OpenClaw / Goose | Capabilities as folders with frontmatter manifests ([OpenClaw](https://docs.openclaw.ai/tools/skills)); per-tool permissions ([Goose](https://goose-docs.ai/docs/guides/managing-tools/goose-permissions/)) | One manifest per capability |
| OVOS | An ordered chain of "solvers", in which non-LLM solvers (e.g. Wikipedia) run before any LLM ([ovos-persona](https://pypi.org/project/ovos-persona/)) | Cheap local solvers ahead of the provider chain |

In short, OpenClaw and Goose (declarative capability manifests) and Home Assistant (local-first routing and streaming voice) are the best systems to learn *architecture* from. Open WebUI is the best to learn *RAG quality* from. OpenHands and Letta are the best to learn *reliability and memory* from. No independent benchmark compares these assistants on answer quality directly, so these judgements rest on documented features, not measured results.

## Retrieval is where Zedek loses answers today

Zedek's current memory path has three weak points that stack on top of each other. `memory.retrieve()` asks Chroma for top_k=3 dense matches. `research_agent.py` then drops any hit whose distance is above `MEMORY_RELEVANCE_MAX_DISTANCE = 1.0`, and `orchestrator.py` uses a similar filter. First, MiniLM L2 distances shift with query length and phrasing, so one fixed cutoff will wrongly reject some good matches and wrongly accept some bad ones. Second, three candidates leave no room for ordering mistakes. Third, a dense-only index handles exact tokens poorly.

**A cross-encoder reranker is the highest-value, lowest-risk fix.** An independent CPU benchmark (January 2026) found that FlashRank's ms-marco-MiniLM-L-12-v2, a model of about 4 MB, added a **mean of 31 ms**. That was about **0.3% of end-to-end time** in a pipeline where the LLM call dominates ([clouatre-labs benchmark](https://github.com/clouatre-labs/rag-reranking-benchmarks)). The largest gain figure is vendor-reported. Anthropic says that adding reranking on top of hybrid retrieval cut top-20 retrieval failures from 2.9% to 1.9%, a 67% total reduction from its 5.7% baseline ([Anthropic](https://www.anthropic.com/news/contextual-retrieval)). A September 2026 academic study used bge-base plus **bge-reranker-base as its "strong baseline"**, which suggests that small rerankers are now the standard default ([arXiv 2609.05637](https://arxiv.org/html/2609.05637)). For Zedek, the change is to retrieve 15–20 candidates, rerank them, keep the top 3, and replace the L2 gate with a threshold on the reranker's score. The threshold should be tuned on a labelled set, because no published figure covers one-sentence personal facts. Larger rerankers such as bge-reranker-v2-m3 (568M) and mxbai-rerank-base-v2 score 53.9–55.6 BEIR nDCG@10. Those scores are vendor-reported and were measured on an A100 GPU only ([Mixedbread](https://www.mixedbread.com/blog/mxbai-rerank-v2)), so their latency on a laptop CPU is unknown and they are not the right starting point.

**BM25 hybrid search is next, and local Chroma cannot do it by itself.** Chroma's BM25/SPLADE support is shown only with `CloudClient` ([Chroma](https://www.trychroma.com/project/sparse-vector-search)). Local users report the error "Sparse vector indexing is not enabled in local" ([chroma #6185](https://github.com/chroma-core/chroma/issues/6185)). The workaround is to keep an in-memory `bm25s` index next to Chroma and merge the two result lists with reciprocal rank fusion, which takes about ten lines of code. BM25S has a peer-reviewed paper that reports **100–500× the throughput of rank_bm25** ([arXiv 2407.03618](https://arxiv.org/pdf/2407.03618)). Independent 2026 results on mixed text and table documents show that hybrid retrieval beats both of its parts on every metric, with up to **+8.1pp Recall@5** ([arXiv 2604.01733](https://arxiv.org/html/2604.01733v1)). Elastic's older, vendor-reported BEIR figure is +18% nDCG@10 over BM25 alone ([Elastic](https://www.elastic.co/search-labs/blog/improving-information-retrieval-elastic-stack-hybrid)). RRF discards absolute scores, which makes the reranker threshold necessary rather than optional.

**The embedding model is also out of date.** snowflake-arctic-embed-s scores **51.98 MTEB retrieval nDCG@10** and bge-small-en-v1.5 scores 51.68. Both have the same 384 dimensions as MiniLM ([Snowflake model card](https://huggingface.co/Snowflake/snowflake-arctic-embed-s); [BAAI model card](https://huggingface.co/BAAI/bge-small-en-v1.5)). Both figures are self-reported on the model cards. Switching models means re-embedding the collection and adding a query-only prefix. The intent router in `classifier.py` has the opposite need. model2vec's potion-base-8M is **up to 500× faster on CPU** and reaches about 92% of MiniLM's MTEB average ([model2vec](https://github.com/MinishLab/model2vec); [potion-base-8M card](https://huggingface.co/minishlab/potion-base-8M)). That makes it a candidate for routing, but not for memory retrieval. The routing eval harness should decide it.

**The research agent should chunk pages instead of truncating them.** `research_agent.gather()` keeps up to 6 sources, and each is head-truncated to 4,000 characters, so any evidence past the first 4k characters is lost. The evidence favours simple methods. A NAACL 2025 study found that semantic chunking's costs "are not justified by consistent performance gains" ([ACL Anthology](https://aclanthology.org/2025.findings-naacl.114/)). An independent 2026 study of eight chunking methods found that **cheap "enriched-title" chunking** (prepending the document title) performed well, while LLM-generated contextual chunking was slow and not a consistent winner ([arXiv 2608.16586](https://arxiv.org/html/2608.16586v1)). The fix is to split each page recursively into chunks of about 250 tokens (MiniLM truncates at 256 word-pieces), prefix each chunk with "title — section", rerank all chunks against the question, and pass only the best ones to `synthesize()`. This should improve which sources get cited and also shrink the prompt.

**Grounding checks should be cheap and local.** CRAG's gains shrank in an independent open-source reproduction to **+3.0pp on PopQA and +0.4pp on ARC**. The same study found that CRAG's evaluator relies mainly on named-entity overlap ([arXiv 2603.16169](https://arxiv.org/abs/2603.16169v1)), which a reranker score already captures at no extra cost. Separately, up to **57% of RAG citations are "post-rationalized"**: the model answers from memory and then cites a document that only looks like a match ([Wallat et al. 2025](https://staff.fnwi.uva.nl/m.derijke/wp-content/papercite-data/pdf/wallat-2025-correctness.pdf)). This argues for a per-sentence check with a small NLI model (MiniCheck RoBERTa or DeBERTa, 0.4B) that tests each [S#] claim against its source ([MiniCheck](https://huggingface.co/bespokelabs/Bespoke-MiniCheck-7B)). Its CPU latency is unmeasured, so it belongs in the second tier. Query rewriting gives small gains of about 1–4pp over a baseline that already has a reranker, and the September 2026 study found that combining methods **hurt AmbigNQ by 2.49pp** ([arXiv 2609.05637](https://arxiv.org/html/2609.05637)). The only rewrite worth doing for personal memory is resolving references like "her" into a standalone question. For research, rewriting should happen only when retrieval confidence is low.

## Quota, not money, is Zedek's scarce resource

The routing literature optimizes dollars. FrugalGPT reports up to 98% cost reduction ([arXiv 2305.05176](https://arxiv.org/abs/2305.05176)) and RouteLLM more than 2× ([arXiv 2406.18665](https://arxiv.org/abs/2406.18665)). Zedek pays nothing, but it runs out of requests. **OpenRouter `:free` allows 50 requests/day** without $10 of purchased credit ([OpenRouter limits](https://openrouter.ai/docs/api/reference/limits)). NVIDIA Build is reported at about 40 RPM ([NVIDIA forums](https://forums.developer.nvidia.com/t/request-for-nvidia-build-api-rate-limit-increase-40-rpm-200-rpm/377433)), and Gemini limits apply per project and reset at midnight Pacific ([Gemini rate limits](https://ai.google.dev/gemini-api/docs/rate-limits)). `TASK_PROVIDERS` in `llm_provider.py` currently lists OpenRouter *first* for `process_reasoning`, so a 50-per-day provider sits at the head of a chain. The cascade idea that carries over is simple. Handle a request locally with zero quota where possible, then try a fast, high-quota model with constrained JSON, and move to scarce quota only when validation fails. Zedek should also record 429s and rate-limit headers so `generate_chat()` skips providers it expects to be exhausted instead of calling them to find out.

**Structured output is the most direct reliability gain.** Today `llm_provider.py` sends only `response_format: json_object`, Gemini's `responseMimeType`, and Ollama `format: "json"`. That forces valid JSON syntax but no schema. Independent benchmarks show why a schema matters. Without constrained decoding, 0.6B–4B models return **7–21% schema-invalid output, and 0% with it** ([arXiv 2609.23742](https://arxiv.org/abs/2609.23742)). JSONSchemaBench found that constrained decoding also *raised* task accuracy by up to about 4 points, for example GSM8K on Llama-3.1-8B going from 80.1% to 83.8% ([arXiv 2501.10868](https://arxiv.org/html/2501.10868v3)). Every provider in the chain has a native schema mode, but each names it differently:

| Provider | Native schema mechanism |
|---|---|
| Gemini | JSON-schema output ([Gemini docs](https://ai.google.dev/gemini-api/docs/structured-output)) |
| Groq | `strict: true`, on GPT-OSS models only ([Groq](https://console.groq.com/docs/structured-outputs)) |
| NVIDIA NIM | `guided_json` / `guided_choice` passed through `extra_body` ([NIM](https://docs.nvidia.com/nim/large-language-models/1.12.0/structured-generation.html)) |
| Ollama (local) | `format=<schema>`, which suits the planned Qwen3 8B ([Ollama](https://docs.ollama.com/capabilities/structured-outputs)) |

Given the decision to avoid LiteLLM, the right design is a hand-written `schema_for(provider, PydanticModel)` adapter. Each response is validated with Pydantic, and on failure Zedek re-asks once with the error text before moving to the next provider. For intent fallback in `classifier.py`, a single-field enum schema is the cheapest and most reliable form, because JSONSchemaBench shows that API schema coverage drops sharply as schemas get more complex.

**Prompt order decides whether provider caches ever hit.** Cerebras caches all models in 128-token blocks, and cached tokens **do not count against the uncached-TPM limit**, which it calls "the primary constraint on throughput" ([Cerebras](https://inference-docs.cerebras.ai/capabilities/prompt-caching)). Groq caches only GPT-OSS models, and cached tokens "operate outside rate limit calculations" ([Groq](https://console.groq.com/docs/prompt-caching)). Gemini's implicit cache needs a prefix of **2,048–4,096 tokens** ([Google](https://ai.google.dev/gemini-api/docs/caching)), so Zedek's short extraction prompts will miss it. The change costs only a couple of hours. Keep system prompts, schemas and few-shot examples byte-identical and first, and put timestamps, memory snippets and the user query last.

**Response caching should be exact-match only.** Measured semantic-cache hit rates are **5–15% on conversational traffic** ([arXiv 2510.26835](https://arxiv.org/abs/2510.26835)). vCache showed that static similarity thresholds produce unpredictable error rates ([arXiv 2502.03771](https://arxiv.org/abs/2502.03771)). A single-user assistant whose questions depend on personal state and time would serve confidently stale answers. A SQLite hash cache for deterministic sub-tasks such as fact canonicalization is safe. A semantic cache over memory, calendar, weather or web intents is not.

**Streaming is the largest perceived-latency win and costs no extra quota.** Home Assistant, reporting its own measurements, found that generating audio from the LLM's first words cut **cloud TTS from 6.62 s to 0.51 s and local Piper from 5.31 s to 0.56 s** ([HA blog](https://www.home-assistant.io/blog/2025/09/11/ai-in-home-assistant/)). This means adding SSE streaming to `generate_chat()` for chat turns only, splitting the output at sentence boundaries, and sending each sentence to TTS in the voice path of `wake_word.py`. The planned Chainlit UI gets token streaming from the same change. A delayed hedge (sending the next provider a request after about the p95 latency) comes from datacenter work, where it cut p99.9 latency from 1,800 ms to 74 ms for 2% more requests ([The Tail at Scale](https://cacm.acm.org/research/the-tail-at-scale/)). With blocking `requests`, a losing call still uses quota, so hedging belongs on voice turns only.

## Agent projects contribute structure, not new capability

**Capability manifests fix Zedek's "edit 4 files" problem.** OpenClaw skills are folders containing a `SKILL.md` with YAML frontmatter. Loading is gated on required binaries and environment variables, and only a compact name-and-description list goes into the prompt. OpenClaw budgets this at **about 24 tokens per skill** before descriptions and drops descriptions first when the list gets too long ([OpenClaw docs](https://docs.openclaw.ai/tools/skills)). Zedek's version would be one `capability.yaml` per capability, holding the name, description, router utterances, tier, input schema and requirements, next to a `handler.py`. A single loader would then generate the routes in `classifier.py`, the MCP tool registration, the entries in `tier_gate.py` and the help text. This is the largest item, at about 3–5 days (my estimate) to migrate 27 tools. It improves quality only indirectly, by removing the drift between those four files. Its schema field can also feed the Pydantic adapter above.

**Core memory blocks complement the settled Graphiti-style bi-temporal schema.** Letta keeps labelled, character-limited blocks (`human`, `persona`) in context at all times, and the agent edits them through tools ([Letta](https://www.letta.com/blog/memory-blocks/)). OpenClaw keeps `USER.md` and `MEMORY.md` on disk, and states that "there is no hidden state" ([OpenClaw memory](https://docs.openclaw.ai/concepts/memory)). For Zedek, a `user_profile` block of 1–2k characters holding name, college, target companies and current courses would remove retrieval misses on the most frequently needed facts. The bi-temporal store would stay the system of record. Storing the blocks as git-tracked markdown makes every change Zedek "learns" diffable and revertible. Anthropic's advice that knowledge bases under 200k tokens can go straight into the prompt ([Anthropic](https://www.anthropic.com/news/contextual-retrieval)) supports this. One gap: no primary source measures the benefit of core blocks against pure RAG for personal assistants.

**The condenser and stuck detection belong in `watchdog.py` and the orchestrator.** In the project's own blog, the OpenHands condenser halved per-turn cost once active and turned quadratic cost growth into linear growth. The benchmark score barely moved: **54% vs 53% on a SWE-bench Verified subset** ([OpenHands blog](https://www.openhands.dev/blog/openhands-context-condensensation-for-more-efficient-ai-agents)). Zedek's free providers have small context windows that differ from one another. Summarizing locally with Qwen3 at about 70% of the smallest window, and running OpenClaw's silent "save anything durable" turn first ([OpenClaw memory](https://docs.openclaw.ai/concepts/memory)), makes long sessions survive a switch between providers. The OpenHands SDK names stuck detection as a core feature ([arXiv 2511.03690](https://arxiv.org/abs/2511.03690)). In Zedek it means flagging repeated identical tool calls or error–retry cycles and stopping to ask the user.

**Voice and routing changes come from Home Assistant.** HA's Speech-to-Phrase generates a closed phrase vocabulary and reaches **about 150 ms on a Pi 5, against 5 s or more for Whisper on a Pi 4** (project-reported). HA also says it is "not for LLMs" ([HA Chapter 9](https://www.home-assistant.io/blog/2025/02/13/voice-chapter-9-speech-to-phrase/)). Vosk's `KaldiRecognizer` accepts a grammar, so Zedek can build a command recognizer from its router utterances and keep the free-form recognizer for Q&A. HA also passes recently handled local commands to the LLM so that follow-up questions work. A 2025 HA regression sent locally handled commands to the LLM ([HA #139415](https://github.com/home-assistant/core/issues/139415)), which is the case for the planned routing eval harness to include a "must stay local" test list. From OpenHands' security model, the useful addition is a risk label that the LLM declares inside the tool call at no extra inference cost ([OpenHands security](https://docs.openhands.dev/sdk/guides/security)). Zedek's effective tier becomes max(rule tier, LLM risk), so the LLM can raise a tier but never lower it. Block's red team got code execution through **invisible zero-width Unicode hidden in calendar invites and recipes** ([Block Engineering](https://engineering.block.xyz/blog/how-we-red-teamed-our-own-ai-agent-)). A roughly 20-line sanitizer for web, RAG and email text is therefore worth adding in `web_agent.py` and `research_agent.py`.

## Ranked adoption plan

The effort figures are my own estimates for a solo student who knows the Zedek codebase. The gains are the cited external evidence, and none of them was measured on Zedek. Start with step 0: build a labelled retrieval eval of 30–50 real queries (roughly half a day), added to the existing routing harness, so that each step below is kept only if it helps.

| # | Recommendation | Expected gain (evidence type) | Effort | Fit for single-user local | Zedek module |
|---|---|---|---|---|---|
| 1 | Cross-encoder reranker (MiniLM-L-6/L-12 or bge-reranker-base): retrieve 15–20, keep 3, use a score threshold instead of L2 ≤ 1.0 | Up to 67% fewer retrieval failures (vendor); +31 ms on CPU (independent) | 0.5–1 day | Excellent; about 4–130 MB of RAM | `memory.py retrieve()`, `research_agent.py` memory gate, `orchestrator.py` fact lookups |
| 2 | Per-provider schema-constrained JSON plus Pydantic validation and one re-ask | Schema-invalid output 7–21% → 0%; up to +4pt task accuracy (independent) | 1–1.5 days | Excellent; no new dependencies beyond Pydantic | `llm_provider.py generate_chat()`, `_openai_compatible`, `_gemini`, `_local`; `classifier.py query_llm_with_tools` |
| 3 | Quota-aware chain: move OpenRouter off the head of `process_reasoning`, track 429s and skip exhausted providers, escalate on validation failure | Fewer wasted requests and less failover latency (inferred from FrugalGPT/RouteLLM, no free-tier study) | 0.5–1 day | Excellent | `llm_provider.py TASK_PROVIDERS`, `generate_chat()` |

Items 1–5 total about four to five working days and address answer quality directly. Items 6–7 address speed and quota. Items 8–15 are structural improvements to schedule after the first batch shows measurable gains on the eval set.

### Not worth adopting

| Idea | Why not for Zedek |
|---|---|
| Anthropic-style LLM contextual retrieval | Designed for long chunked documents; facts are already self-contained; an independent study found it slow, costly and not consistently better ([arXiv 2608.16586](https://arxiv.org/html/2608.16586v1)). Use the free title prefix instead |
| Semantic or late chunking | No consistent gain over token chunking ([NAACL 2025](https://aclanthology.org/2025.findings-naacl.114/)); late chunking did poorly at scale ([arXiv 2608.16586](https://arxiv.org/html/2608.16586v1)) |
| HyDE or multi-query on personal memory | Invented "hypothetical" user facts pull in wrong memories; ensembles hurt AmbigNQ by 2.49pp and cost an LLM call each ([arXiv 2609.05637](https://arxiv.org/html/2609.05637)) |
| Self-RAG, multi-round reflection, full CRAG with web fallback | Self-RAG needs a fine-tuned generator; CRAG's independent gain is +0.4–3.0pp for extra calls ([arXiv 2603.16169](https://arxiv.org/abs/2603.16169v1)); the reranker score captures most of it |
| Semantic response cache (GPTCache-style) | 5–15% conversational hit rate ([arXiv 2510.26835](https://arxiv.org/abs/2510.26835)) with a high risk of stale personal answers |
| Always-parallel provider fan-out, speculative (PredGen-style) generation | Doubles quota burn on 20–50 RPD/RPM budgets; wrong guesses waste requests |
| Learned router (RouteLLM) | Built for cost differences between paid models; rule order plus validation-driven escalation captures the value |
| Instructor or Outlines | Instructor pulls in SDK clients, which cuts against the settled no-LiteLLM choice; Ollama's `format` already does grammar-constrained decoding locally, so Outlines adds nothing |
| Large rerankers (bge-reranker-v2-m3, mxbai-v2) at first | Only GPU latency is published; start small and move up only if the eval shows a gap |
| OpenClaw's public skill registry, network gateway and messaging bridges | ClawHub had over 1,184 malicious skills ([Sangfor](https://www.sangfor.com/blog/cybersecurity/openclaw-ai-agent-security-risks-2026)); the CVE-2026-25253 WebSocket hijack gave RCE on the localhost gateway ([BetterClaw](https://www.betterclaw.io/blog/openclaw-security-2026)). If Chainlit exposes a port, bind it to 127.0.0.1 and check Origin |
| Enterprise and multi-user features (RBAC/SSO, 13 vector DB backends, visual flow builders, OVOS MessageBus/HiveMind, remote Docker/VM runtimes, Letta server stack) | Built for many users and many machines; Zedek has one user, one process, bubblewrap and ChromaDB ([Open WebUI](https://docs.openwebui.com/features/); [OVOS](https://openvoiceos.github.io/ovos-technical-manual/)) |
| Speech-to-Phrase-style closed vocabulary for open Q&A | HA itself says it is "not for LLMs" and cannot handle open text ([HA Chapter 9](https://www.home-assistant.io/blog/2025/02/13/voice-chapter-9-speech-to-phrase/)) |

## Conclusion

The research leads to a clear conclusion: at Zedek's scale, the model is not the bottleneck and neither is the framework. The weak point is the few hundred milliseconds between a question and the three facts or six truncated pages the LLM gets to see, plus the requests lost to malformed JSON and exhausted providers. Those are cheap, local fixes that run on a CPU. Borrowing more ambitious ideas from the popular agent projects produces less improvement per hour of work until they are done.

The largest uncertainty is that almost every gain figure comes from corpora of 10k+ documents, from vendors, or from GPU hardware. Nobody has published a benchmark on a single user's few hundred short facts. That makes the small eval set the most valuable thing to build first, and it changes how every later decision gets made: the reranker threshold, the choice of embedding model and whether an NLI check pays off all become measured choices instead of guesses taken from other people's benchmarks.
